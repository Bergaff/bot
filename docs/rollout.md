# Обкатка авто-сбора (этап 7)

План ввода авто-сбора в работу: неделя, по шагам, с критерием перехода на каждый шаг.
Цель обкатки — убедиться, что сборщик **не ломает** основной поток заявок из бота,
не забивает очередь модерации мусором и не нарывается на ограничения Telegram.

Согласно ТЗ (п. 3.7) новые чаты добавляются в обход только после проверки, что у них
есть веб-превью, — для этого есть `scripts/probe-chats.mjs`.

Порядок: **день 0** — репетиция без интернета → **день 1** — dry run на проде →
**день 2** — первый боевой прогон руками → **дни 3–7** — cron и наблюдение →
**параллельно/после** — обкатка расширения на аккаунте заказчика.

---

## 0. Чек-лист готовности (до первого шага)

- [ ] Миграция `0004_ingest.sql` применена (`wrangler d1 migrations apply parcel --remote`),
      таблица `watch_chats` есть, у `listings` появился столбец `origin`.
- [ ] Секреты заданы: `wrangler secret put ADMIN_API_TOKEN`, `wrangler secret put INGEST_TOKEN`
      (токен расширения можно задать позже — до его обкатки).
- [ ] `wrangler.toml`: cron ещё **не** включён — обкатку начинаем с ручных прогонов.
      ```toml
      [triggers]
      crons = []          # на день 0–2 пусто
      ```
- [ ] `COLLECT_ENABLED=1` в `[vars]` (ручной прогон работает и при `0`, но cron — нет).
- [ ] Настроечные значения на обкатку (порог 1 чат, 1 страница — чтобы не шуметь):
      ```toml
      [vars]
      COLLECT_ENABLED = "1"
      COLLECT_MAX_CHATS = "2"
      COLLECT_MAX_PAGES = "1"
      COLLECT_MAX_AGE_DAYS = "3"
      COLLECT_MAX_FETCHES = "8"
      COLLECT_AI_DAILY_LIMIT = "20"
      ```
- [ ] Админ знает, как смотреть очередь модерации: заявки авто-сбора приходят со статусом
      `pending` и бейджем «сборщик» / «расширение» (этап 6). `AUTO_APPROVE` на них не действует.
- [ ] Есть человек, который каждый день проглядывает созданные заявки и фиксирует,
      что нужно подкрутить (это и есть обкатка).

Проверить, что API жив, можно одной командой:

```bash
curl -s -H "Authorization: Bearer $ADMIN_API_TOKEN" \
  https://<ваш-домен>/api/admin/collect/status | jq .
```

## 1. День 0 — репетиция без интернета (30 минут)

Задача: потренироваться на фикстурах, прежде чем трогать прод. Нужен только Node ≥ 22.18.

```bash
npm install
node parcel/demo/server.mjs          # http://localhost:8790
```

Демо поднимает настоящую админку (`parcel/demo/`) + настоящий API (`src/server.ts`) на
локальном sqlite и зеркало `t.me/s/` на фикстурах. В нём можно:

1. добавить чат в обход (`durov`, `drivers_pl_by`, `broken_channel`);
2. нажать «запустить сбор сейчас» → увидеть отчёт прогона и заявки в очереди с бейджем
   «сборщик» и ссылкой на исходное сообщение;
3. сломать чат (`broken_channel`) и посмотреть, как работают 3 попытки, авто-отключение
   и алерт;
4. прогнать разведку и мониторинг против зеркала:

```bash
node scripts/probe-chats.mjs durov drivers_pl_by gone_channel broken_channel \
  --base-url http://127.0.0.1:8790/mirror/s

node scripts/collect-report.mjs --url http://127.0.0.1:8790 --token demo-admin-token
```

**Критерий перехода:** отчёт прогона читается, заявки видны в очереди, `collect-report.mjs`
показывает проблемы по сломанному чату и возвращает код 1.

Тот же сценарий без браузера на каждом пуше прогоняет CI: воркфайл `docs/ci/ci.yml`, job
`smoke` (зеркало → разведка чатов → dry run → боевой прогон → сброс курсора → дубликаты по
`tg_seen`). Если он зелёный, серверная часть обкатки собрана правильно. Включить:
скопировать воркфайлы в `.github/workflows/` — см. [`docs/ci/README.md`](ci/README.md).

## 2. День 1 — разведка чатов и dry run на проде

### 2.1 Отобрать чаты (ТЗ п. 3.7)

Составьте список кандидатов (городские чаты попуток, «подвезу/ищу попутку», доски объявлений)
и прогоните разведку. Она не добавляет ничего в обход — только отвечает, стоит ли добавлять:

```bash
node scripts/probe-chats.mjs drivers_pl_by posylki_minsk avtopoputki_by --deep
```

Для каждого чата видно: открывается ли веб-превью (`t.me/s/<username>`), тип
(канал / супергруппа), сколько сообщений за последние N дней, сколько из них похоже на
объявления и сколько на «пассажирский трёп», и вердикт:

| Вердикт | Что значит | Действие |
|---|---|---|
| `добавлять` | превью есть, чат живой, объявления находятся | добавляем в обход |
| `проверить вручную` | превью есть, но объявлений мало/не распознаны, или это канал | открыть `t.me/<username>` глазами, решить самим |
| `не добавлять` | превью не отдаётся (`missing`), чат закрыт (`blocked`), пустой или мёртвый (>30 дней без сообщений) | вычеркнуть; для закрытых чатов — только расширение |

Диагнозы, которые возвращает разведка: `missing` (превью не отдаётся — чат приватный или
удалён), `blocked` (Telegram требует вход), `markup_changed` (страница отдаётся, но сообщения
не распознаны — см. раздел 6), `empty`, `http_404`, `network`, `stale`.

### 2.2 Добавить 2 чата

Через админку (вкладка «чаты» → «добавить чат») или API:

```bash
curl -s -X POST https://<ваш-домен>/api/admin/watch-chats \
  -H "Authorization: Bearer $ADMIN_API_TOKEN" -H "Content-Type: application/json" \
  -d '{"username":"drivers_pl_by","kind":"supergroup"}'
```

`kind` можно не указывать — определится сам при первом прогоне.

### 2.3 Прогнать в режиме dry run

`dryRun` не трогает базу вообще: ни заявок, ни `tg_seen`, ни курсоров.

```bash
curl -s -X POST https://<ваш-домен>/api/admin/collect \
  -H "Authorization: Bearer $ADMIN_API_TOKEN" -H "Content-Type: application/json" \
  -d '{"dryRun":true}' | jq '.report.totals, [.report.chats[] | {username, status, fetched, new, created, skipped, duplicate, error}]'
```

Прогон одного чата: `-d '{"chatId":"web:drivers_pl_by","dryRun":true}'`.

Что видно в отчёте:

| Поле | Смысл |
|---|---|
| `totals.fetched` | сколько сообщений сняли со страниц |
| `totals.new` | из них новее курсора и не старше `COLLECT_MAX_AGE_DAYS` |
| `totals.created` | сколько распознано как объявления |
| `totals.skipped` | отсеяно: пассажирский трёп, без маршрута, слишком старые/длинные |
| `totals.duplicate` | уже обработанные раньше (`tg_seen`) — штатный ответ, не ошибка |
| `totals.errors`, `totals.disabled` | должно быть 0 |
| `totals.fetches` | сколько сетевых запросов потрачено (сравнить с `COLLECT_MAX_FETCHES`) |
| `chats[].status` | `ok` / `empty` / `missing` / `blocked` / `markup_changed` / `http_404` / `network_error` |
| `chats[].cursorBefore → cursorAfter` | движение курсора |
| `aiQuotaLeft` | остаток дневной квоты ИИ сборщика (в dry run ИИ не списывается) |
| `config` | с какими настройками реально прошёл прогон |

Сами **поля** разобранных объявлений в отчёт не кладутся (иначе он раздувается на сотнях
сообщений). Качество разбора проверяют через `POST /api/ingest` с `dryRun: true` на паре
настоящих текстов из чата — это тот же конвейер, что и у сборщика:

```bash
curl -s -X POST https://<ваш-домен>/api/ingest \
  -H "Authorization: Bearer $INGEST_TOKEN" -H "Content-Type: application/json" \
  -d '{"collector":"manual-check","dryRun":true,"messages":[{
        "chatId":"web:drivers_pl_by","messageId":900001,
        "date":"2026-09-15T18:00:00Z",
        "text":"25.09 Варшава — Брест, возьму посылку до 20 кг, 40 BYN, +48 579 264 254"}]}' \
  | jq '.results[0].fields'
# → [{"type":"offer","fromCity":"Варшава","toCity":"Брест","departureDate":"2026-09-25",
#     "description":"25.09 Варшава — Брест, возьму посылку до 20 кг, 40 BYN"}]
# телефон ушёл в контакты, заявка не создана (dryRun) — проверяем только поля
```

Локально то же самое: `npm run server` и `node local/cli.ts ingest --dry --text "…"`;
сырые сообщения страницы — `npm run scan -- drivers_pl_by --html p.html`.

**Критерий перехода:**

- `created + skipped + duplicate ≈ new`, `errors = 0` (ничего не теряется молча);
- города и даты в `fields` **правильные** — это главный критерий;
- у обоих чатов `status: "ok"`, `error` пустой, `fetched > 0`;
- очередь модерации пуста (dry run ничего не создал).

Если распознавание плохое — cron не включаем, сначала раздел 6 («тюнинг»).

## 3. День 2 — первый боевой прогон

Тот же вызов без `dryRun`:

```bash
curl -s -X POST https://<ваш-домен>/api/admin/collect \
  -H "Authorization: Bearer $ADMIN_API_TOKEN" -H "Content-Type: application/json" \
  -d '{}' | jq .report.totals
```

Что должно произойти:

1. Заявки созданы со статусом `pending` и `origin='collector'`, у каждой `sourceChatId`
   вида `web:<username>` и `sourceMessageId` — в карточке модератора кликабельная ссылка
   «исходное сообщение» на `t.me/<username>/<id>`.
2. Админам ушло уведомление (как на обычную заявку).
3. Повторный прогон тут же даёт `duplicate` и **не** создаёт копии — это проверка
   `tg_seen`-дедупликации. Прогоните дважды подряд и сравните `totals.created`:
   во второй раз должно быть 0.
4. Дневной лимит ИИ бота (`ai:day:*`, 300) **не изменился** — сборщик расходует свой
   счётчик (`ai:collect:day:*`). Проверьте в `GET /api/admin/collect/status` → `ai`.

Затем **вручную промодерируйте все созданные заявки**: города, даты, контакты, ссылку на
источник. Записывайте каждую ошибку — это вход для тюнинга.

**Критерий перехода:** ни одной заявки с выдуманными городами или битой ссылкой; дубли не
создаются; лимит ИИ бота не тронут.

## 4. Дни 3–7 — cron и наблюдение

### 4.1 Включить cron

```toml
[triggers]
crons = ["17 */2 * * *"]     # каждые 2 часа, в :17
```

`COLLECT_CRON` в `[vars]` должен совпадать с этим выражением. `npm run deploy`.

Ротация: за один прогон обходится не больше `COLLECT_MAX_CHATS` чатов (курсоры у каждого свои), поэтому на 6 чатах и cron раз в 2 часа каждый чат проверяется примерно раз в 6 часов.

### 4.2 Ежедневный контроль

Один раз в день (лучше утром) — сводка:

```bash
node scripts/collect-report.mjs --url https://<ваш-домен> --token $ADMIN_API_TOKEN \
  --stale-hours 6
```

Скрипт печатает: включён ли cron, задан ли `INGEST_TOKEN`, сколько чатов в обходе и сколько
с ошибками, остатки квот ИИ, счётчики заявок по источникам, статистику расширения за сегодня,
итоги последнего прогона и список проблем. Код возврата 1 — если есть проблемы:

```bash
# для cron/CI/healthchecks.io
node scripts/collect-report.mjs --url "$URL" --token "$TOKEN" --fail-on errors,disabled,stale
```

Ключи `--fail-on`: `errors` (чат с ошибкой), `disabled` (авто-отключён), `stale` (давно не
проверяли — порог `--stale-hours`, по умолчанию 6), `token` (не задан `INGEST_TOKEN`),
`quota` (квота ИИ на исходе), `empty` (последний прогон ничего не нашёл или был dry run).
Без `--token` берётся `ADMIN_API_TOKEN` из окружения; `--json` — для своих дашбордов.

Куда повесить сводку — варианты:

- **GitHub Actions (воркфайл уже в репозитории)** — `docs/ci/monitor.yml` (скопировать в
  `.github/workflows/`, см. [`docs/ci/README.md`](ci/README.md)): каждые
  3 часа (`25 */3 * * *`, через ~8 минут после обхода воркера) и вручную через «Run workflow»
  (там же можно поменять `--stale-hours` и список `--fail-on`). Падение прогона = письмо от
  GitHub, отчёт — в job summary. Включается двумя настройками (Settings → Secrets and
  variables → Actions): переменная `COLLECT_REPORT_URL` = `https://<ваш-домен>` и секрет
  `COLLECT_ADMIN_TOKEN` = `ADMIN_API_TOKEN`. Пока переменная не задана, job пропускается.
  Расписание работает только из default-ветки, поэтому воркфайл должен попасть в `main`.
- **Своя cron-машина**: `25 9 * * * cd /path/to/repo && node scripts/collect-report.mjs … || уведомление`.
- **Healthchecks.io** (dead man's switch): тот же запуск с
  `--fail-on errors,disabled,stale,token`; код 1 → алерт, а если запуск вовсе не состоялся —
  алерт придёт от самого сервиса (ловит «умерший cron» лучше всего).

Код возврата 1 — это проблемы из `--fail-on`. Остальное в отчёте тоже видно: предупреждения
(квота ИИ на исходе, пустой прогон, ошибки последнего прогона, нет чатов в обходе) и проблемы
вне списка `--fail-on` — итоговая строка подскажет, что смотреть.

### 4.3 Что смотреть каждый день

| Метрика | Где | Норма на обкатке |
|---|---|---|
| Заявок создано сборщиком | `listingsByOrigin.collector` | растёт; 5–30 в сутки на 2–3 чатах |
| Отсеяно | `report.totals.skipped` | больше, чем `created` — это нормально (трёп) |
| Дубли | `report.totals.duplicate` | растёт от прогона к прогону — значит дедупликация работает |
| Ошибки чатов | `watchChats.withErrors`, `report.totals.errors` | 0 |
| Авто-отключения | `report.totals.disabled` | 0 |
| Квота ИИ сборщика | `ai.collectLeft` | не ноль к концу суток (иначе разбор деградирует до правил) |
| Квота ИИ бота | ключ `ai:day:<дата>` в KV (существующий счётчик бота) | **не меняется** из-за сборщика |
| Прогоны | `lastReport.startedAt` | не старше `--stale-hours` (cron жив) |

### 4.4 Дни 5–7 — расширение на аккаунте заказчика

Серверная часть к этому времени уже обкатана. Расширение ставится на **отдельный** аккаунт
заказчика (ТЗ, раздел «Ограничения»), порядок:

1. `wrangler secret put INGEST_TOKEN`; в админке на вкладке «чаты» появится строка про токен.
2. Установить расширение (`extension/` — распакованное, или `userscript/poputchka-collector.user.js`
   через Tampermonkey), открыть `web.telegram.org`, войти аккаунтом заказчика.
3. В попапе задать `serverUrl` и `token`, **whitelist из 1–2 чатов** (всё остальное расширение
   не читает вообще), `intervalSec = 180`, `confirmMode = ON`.
4. Нажать «Пауза» → снять паузу, убедиться, что счётчики (`найдено / отправлено / создано /
   дубликаты / пропущено`) двигаются, а в логе нет ошибок.
5. Проверить на сервере: `extensionToday.messages > 0`, `listingsByOrigin.extension` растёт,
   заявки в очереди с бейджем «расширение».
6. Через 2–3 дня стабильной работы — снять `confirmMode` и поднять `intervalSec` до 180–300.

Критерии остановки расширения: 401/503 (показывает ошибку и встаёт), «не могу прочитать
сообщения» (изменилась разметка Telegram Web) — тогда пауза и разбор, а не молчаливая работа.

**Расширение — только чтение.** Никаких кликов, отправки, реакций, пересылок. Это не
обсуждается и на обкатке проверяется глазами: аккаунт заказчика не должен ничего писать.

### 4.5 Критерий завершения обкатки (конец дня 7)

- [ ] 5 дней подряд cron отработал без `errors` и `disabled`;
- [ ] создано ≥ 30 заявок авто-сбором, из них ≥ 70% опубликованы модератором **без правок**
      городов и дат;
- [ ] ни одной заявки с битой ссылкой на исходное сообщение;
- [ ] лимит ИИ бота (`ai:day:*`) за эти дни расходовался так же, как до включения сборщика;
- [ ] дубли при повторных прогонах не создаются;
- [ ] расширение (если обкатывалось) 2 дня подряд отправляло сообщения без 401/429/`markup`-ошибок;
- [ ] админ знает, где смотреть сводку и как остановить сбор (раздел 7).

После этого можно поднять `COLLECT_MAX_CHATS` до 5–10, `COLLECT_MAX_AGE_DAYS` до 7 и
оставить cron `17 */2 * * *`.

## 5. Сколько чатов можно добавить

Ограничение — не Telegram, а бюджет подзапросов воркера: на бесплатном тарифе ~50 `fetch`
на один вызов cron. Один чат = `COLLECT_MAX_PAGES + 1` запросов к `t.me/s/`.

```
COLLECT_MAX_FETCHES ≥ COLLECT_MAX_CHATS × (COLLECT_MAX_PAGES + 1)
```

При `MAX_CHATS=10`, `MAX_PAGES=2` нужно 30 запросов — запас есть. Между запросами к одному
чату сборщик выдерживает паузу (`delayMs`), а 429 от `t.me` обрабатывает по `Retry-After`.

## 6. Тюнинг: симптомы и что крутить

| Симптом | Причина | Что сделать |
|---|---|---|
| `markup_changed` у всех чатов, `fetched = 0` при живой странице | Telegram поменял вёрстку `t.me/s/` | поправить селекторы в `src/preview-html.ts`, прогнать `npm test` (`tests/collect-html.test.ts`), задеплоить, «сбросить ошибки» в админке |
| Чат авто-отключился (`disabled`) | 3 прогона подряд с ошибкой, или диагноз `missing` (превью не отдаётся) | разобраться в причине; приватный чат — убрать из обхода, он доступен только расширением |
| `created = 0` при большом `fetched` | чат пассажирский (обсуждения, а не объявления) | вычеркнуть чат; разведка это показывает заранее (`не добавлять`) |
| Города определяются неверно | правила парсера не знают города/направления | дополнить словарь в `src/parser.ts` (или в `parcel/src/parser.ts` после переноса) |
| Объявлений мало, но они есть | ИИ-ступень не включилась: нет `AI_API_KEY` или кончилась квота | `wrangler secret put AI_API_KEY`, поднять `COLLECT_AI_DAILY_LIMIT` |
| Много обращений к ИИ, квота уходит к обеду | слишком много «трудных» сообщений | уменьшить `COLLECT_AI_DAILY_LIMIT` — разбор продолжится правилами, сбор не встанет |
| 429 от `t.me` | слишком агрессивный обход | уменьшить `COLLECT_MAX_FETCHES`, реже cron (раз в 3–4 часа) |
| 429 от своего `/api/ingest` (расширение) | короткий интервал опроса / большой батч | в попапе: `intervalSec` 180+, батч ≤ 20; расширение само ждёт `Retry-After` |
| `skipped:too_old` у всех сообщений | `COLLECT_MAX_AGE_DAYS` меньше, чем активность чата | поднять до 7 (для обкатки на фикстурах — см. демо) |
| Заявок слишком много, модерация не успевает | чатов больше, чем нужно | сократить обход до 2–3 самых плотных чатов, `COLLECT_MAX_PAGES=1` |

Локальная отладка без деплоя — CLI:

```bash
npm run db:local                                        # создать локальную sqlite вместо D1/KV
node local/cli.ts watch-chats add drivers_pl_by --kind supergroup
node local/cli.ts collect --dry --chat drivers_pl_by    # --json — полный отчёт
node local/cli.ts watch-chats list                      # курсоры, счётчики, ошибки
node local/cli.ts report                                # последний прогон (из KV)
node local/cli.ts daemon --every 3600                   # локальная замена cron
```

Против зеркала фикстур (без интернета): `node local/mock-tme.mjs` и
`--base-url http://127.0.0.1:8899/s --no-delay` у `collect`.

## 7. Как остановить и откатиться

По возрастанию жёсткости:

1. **Пауза одного чата** — админка → «выключить» (или `PUT /api/admin/watch-chats/:id`
   `{"enabled":false}`). Остальные продолжают собираться.
2. **Пауза расширения** — кнопка «Пауза» в попапе. Сервер при этом не трогается.
3. **Остановить cron-сбор** — `COLLECT_ENABLED=0` в `[vars]` и redeploy (или убрать выражение
   из `crons`). Ручной прогон через API продолжит работать — это удобно для проверки.
4. **Отозвать доступ расширения** — `wrangler secret delete INGEST_TOKEN`.
   `/api/ingest` начнёт отвечать 503, расширение остановится и покажет ошибку.
5. **Убрать созданные заявки** — они все в `pending`, поэтому в публичный каталог не попали:
   ```sql
   -- посмотреть, что создал авто-сбор
   SELECT id, type, from_city, to_city, origin, source_chat_id, source_message_id, created_at
     FROM listings WHERE origin != 'bot' AND status = 'pending';
   -- удалить (осторожно: сначала проверьте выборку SELECT-ом)
   DELETE FROM listings WHERE origin != 'bot' AND status = 'pending';
   ```
   `tg_seen` при этом трогать не нужно: если чат вернуть в обход, уже виденные сообщения
   останутся отсеянными как `duplicate`. Чтобы пересобрать чат с нуля — «сбросить курсор»
   в админке **и** удалить его строки из `tg_seen`:
   ```sql
   DELETE FROM tg_seen WHERE chat_id = 'web:drivers_pl_by';
   ```
6. **Полный откат** — удалить файлы из раздела «что копировать» (`INTEGRATION.md`, раздел 0),
   убрать cron и переменные из `wrangler.toml`. Миграция 0004 обратно не откатывается
   (столбец `origin` и таблица `watch_chats` остаются) — они не мешают основному потоку:
   `origin` по умолчанию `'bot'`, пустая `watch_chats` ничего не делает.

## 8. Что не должно измениться

Обкатка считается проваленной, если после включения авто-сбора:

- заявки из бота стали обрабатываться медленнее или теряться (проверьте ключ `ai:day:<дата>`
  в KV — общий лимит ИИ бота сборщиком **не** расходуется);
- `AUTO_APPROVE` начал публиковать собранные заявки (собранные **всегда** `pending` —
  это зашито в коде, а не в настройке);
- аккаунт заказчика получил ограничение от Telegram (признак: расширение пишет в чат,
  кликает, ставит реакции — этого быть не должно; или интервал опроса < 60 с);
- очередь модерации заполнилась дубликатами одного и того же объявления.
